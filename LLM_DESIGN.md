# LLM Design

Цей файл — не “документація для замовника”.
Це памʼять проекту: навіщо тут LLM і як саме ми її використовуємо.

---

## Загальна ідея

Ми не будуємо “бота з правилами”.
Ми будуємо систему, де:

- **Core** — тупий, чесний виконавець
- **LLM** — думає, розуміє і спілкується
- **Користувач** — говорить як людина
- **Код** — не імітує мислення

---

## Core (ядро)

Core — це механізм, який змінює стан бази.

Він:
- приймає лише валідні JSON-команди
- виконує їх детерміновано
- нічого не знає про:
  - користувачів
  - мову
  - сенс запиту
  - LLM або “штучний інтелект”

Core **НЕ**:
- намагається зрозуміти, що “мав на увазі” користувач
- працює з категоріями (“медичне”, “інструменти”)
- має синоніми
- веде діалог

> Core — це руки. Не мозок.

---

## CLI

CLI — це адміністративний і debug-інтерфейс.

Він:
- напряму працює з core
- дозволяє виконувати команди вручну
- показує стан складу
- використовується для тестування і відладки

Важливо:
CLI також використовується як **debug-вікно користувацького інтерфейсу**:
я можу писати туди запити “як користувач” і бачити,
що піде користувачу і що відбувається всередині.

CLI **не є** кінцевим користувацьким інтерфейсом.

---

## LLM (штучний інтелект)

LLM — це “людський оператор складу”.

Вона:
- спілкується з користувачем живою мовою
- розуміє:
  - помилки
  - суржик
  - синоніми
  - категорії
- аналізує стан складу
- приймає рішення
- формує команди для core
- формує відповідь користувачу

LLM — **єдиний компонент**, який:
- “розуміє сенс”
- “думає”
- “приймає рішення”

Код **не повинен дублювати її мислення**.

---

## Потік роботи

1. Користувач надсилає повідомлення (текст, згодом аудіо/картинку).
2. Система передає LLM контекст:
   - текст запиту
   - активний склад (один, фіксований)
   - стан складу (повний або стислий)
   - кілька попередніх повідомлень (для діалогу)
3. LLM:
   - розуміє, що хоче користувач
   - вирішує, чи це дія, чи питання
   - формує список команд для core (може бути кілька)
   - формує людську відповідь користувачу
4. Core виконує команди.
5. Користувач отримує відповідь.

---

## Контракт LLM → система

LLM повертає **один JSON**:

```json
{
  "assistant_text": "Відповідь користувачу українською мовою",
  "commands": [
    {
      "command": "intake | move | consume | list",
      "payload": {},
      "storage_id": "active_storage_id"
    }
  ],
  "need_more_info": false,
  "questions": []
}
```

Пояснення:

assistant_text — завжди українською, дружньо, без технічної хуйні

commands може бути порожнім (якщо це питання або розʼяснення)

commands може містити кілька команд

need_more_info=true — LLM хоче уточнення

questions — короткі питання до користувача (1–3)

Діалоги

Діалоги дозволені.

LLM може:

ставити уточнюючі питання

продовжувати розмову

памʼятати контекст у межах діалогу

Якщо діалоги заважатимуть — ми їх обмежимо пізніше.
Зараз пріоритет — природна взаємодія.

Якість відповідей користувачу

Заборонені відповіді типу:

“Переформулюй запит”

“Невірна команда”

Натомість:

пояснити, що саме не зрозуміло

запропонувати варіанти

бути ввічливим і дружнім

Приклад:

“Я не зовсім зрозумів, скільки саме потрібно списати. Можеш уточнити кількість?”

“Не знайшов ‘фляги’. Можливо, ти мав на увазі ‘пляшка води’?”

Помилки і безпека

Ми свідомо не робимо корпоративну параною.

Замість цього:

є журнал усіх дій

є бекапи

є можливість відкотити або виправити помилки

LLM може помилятися — це нормально.
Система має бути зручною для людей, а не стерильно ідеальною.

Принципи

Не дублювати мислення LLM у коді

Не ускладнювати ядро

Робити просто, ефективно і сучасно

Використовувати можливості ІІ, а не боротися з ними
