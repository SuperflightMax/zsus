# LLM Design

Этот документ описывает роль и устройство LLM в системе.
Он фиксирует архитектурные принципы и форму взаимодействия, не зависящие от текущего этапа развития (MVP или далее).

---

## Роль LLM

LLM используется как интерпретатор и голос человеко-ориентированного интерфейса системы.

LLM:
- понимает человеческий ввод
- интерпретирует намерение пользователя
- формирует DraftCommand
- генерирует человеко-понятный ответ пользователю

LLM не:
- выполняет действия
- принимает решения о выполнении
- вызывает core engine напрямую
- изменяет состояние системы

Фактическое выполнение действий и изменение состояния всегда остаётся за системой.

Для конечного пользователя LLM является основным UX-интерфейсом взаимодействия с системой.

---

## Interaction Context

Система работает не с отдельными запросами, а с контекстом взаимодействия (Interaction Context).

Interaction Context — это структурированное описание текущего взаимодействия пользователя с системой.
Даже если взаимодействие состоит из одного шага, форма контекста всегда многошаговая.

### Причины такого подхода
- единая модель для single-turn и multi-turn взаимодействий
- отсутствие необходимости менять архитектуру при добавлении диалога
- контролируемая и расширяемая передача контекста в LLM

### Структура Interaction Context

```json
{
  "interaction_id": "uuid",
  "language_policy": {
    "input": "any",
    "output": "uk"
  },
  "turns": [
    {
      "role": "user",
      "content": "переложи аптечку"
    }
  ]
}
```

turns всегда является массивом
LLM всегда получает Interaction Context целиком, а не отдельную строку ввода.

## Двухпроходная модель работы LLM

LLM используется в двух логических проходах.

### LLM PASS 1 — Интерпретация

Вход
Interaction Context
список разрешённых намерений
режим работы (например, MVP)

Выход
DraftCommand
confidence (уровень уверенности интерпретации)

LLM на этом этапе:
интерпретирует последнее пользовательское сообщение в контексте всего Interaction Context
формирует DraftCommand
не принимает решений о выполнении

### DraftCommand и ExecutableCommand

DraftCommand
DraftCommand — это промежуточное описание намерения пользователя.

DraftCommand:
формируется LLM
может быть неполным
содержит уровень уверенности
никогда не исполняется напрямую
DraftCommand используется системой исключительно для валидации и принятия решения.

ExecutableCommand
ExecutableCommand — это полностью валидированная и детерминированная команда, готовая к выполнению ядром.

ExecutableCommand:
формируется только системой
всегда содержит все необходимые параметры
передаётся в core engine для выполнения
LLM никогда не формирует ExecutableCommand и не вызывает core engine напрямую.

### Policy и Validation

Система выполняет валидацию DraftCommand независимо от LLM.

Валидация включает:
проверку допустимости намерения
проверку наличия обязательных данных
применение дефолтов
оценку уровня уверенности

Результатом валидации является машинно-описанный результат (Validation Result), который используется далее системой и LLM.

### LLM PASS 2 — Ответ оператором

Вход
LLM получает агрегированный контекст, включающий:
Interaction Context
DraftCommand
confidence
результат валидации
результат выполнения (если был)

Пример входного контекста:

```json
Copy code
{
  "interaction_context": { ... },
  "draft_command": { ... },
  "confidence": 0.81,
  "validation": {
    "status": "rejected",
    "reason": "missing_target_location"
  },
  "execution_result": null
}
```

Выход
финальный человеко-понятный ответ пользователю

LLM:
объясняет пользователю результат работы системы
не предлагает вариантов
не задаёт вопросов
не инициирует новые шаги взаимодействия

## Языковая политика
Ввод пользователя может быть на любом языке, включая смешанный.

Ответы пользователю:
всегда формируются на украинском языке
не содержат технических деталей или служебной информации
Языковая политика является обязательной и не может быть переопределена интерфейсами.

## Наблюдаемость и контроль

Все промежуточные данные:
Interaction Context
DraftCommand
confidence
результаты валидации
ответы LLM
должны быть доступны в служебном выводе системы для отладки и анализа.

Это является осознанным архитектурным решением, направленным на повышение доверия к системе и упрощение дальнейшего развития.
