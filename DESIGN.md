# Storage Bot Core — High Level Design

## 1. Общая идея

Storage Bot Core — это система складского учёта с интеллектуальным интерфейсом.
Проект строится как **ядро бизнес-логики**, поверх которого подключаются
различные интерфейсы (CLI, мессенджеры, приложения).

Система проектируется с учётом:
- множества независимых складов
- работы с текстом, голосом и изображениями
- масштабирования и расширения функционала без переписывания ядра

---

## 2. Ключевые принципы архитектуры

- **Единый codebase — множество складов**
- **Полная изоляция складов**
- **Бизнес-логика не зависит от интерфейсов**
- **LLM — переводчик намерений, не исполнитель**
- **Все изменения данных проходят только через ядро**
- **Безопасное поведение при ошибках**
- **Всё должно быть тестируемо без мессенджеров**

---

## 3. Модель складов

### 3.1. Общая модель

Система поддерживает произвольное количество складов.
Каждый склад является полностью изолированной сущностью.

Изоляция означает:
- отдельную базу данных
- отдельное хранилище медиа-файлов
- независимый жизненный цикл

### 3.2. Пример структуры хранения

```
storages/
├─ kharkiv_1/
│ ├─ db.sqlite
│ ├─ media/
│ │ ├─ images/
│ │ └─ audio/
│ └─ logs/
├─ kyiv_2/
│ └─ ...
└─ registry.json
```

`registry` используется для хранения информации о существующих складах и их конфигурации.
Он не содержит бизнес-логики.
В MVP создание/удаление складов и управление конфигурацией выполняется вручную через инфраструктурные команды (без публичного интерфейса).

---

## 4. Пользователи и доступ

### 4.1. MVP-модель

- каждый пользователь привязан ровно к одному складу
- пользователь не выбирает склад вручную
- интерфейс всегда работает в контексте одного склада

Это упрощает UX, логику LLM и тестирование.

### 4.2. Будущее расширение

В будущем возможно:
- доступ к нескольким складам
- роли (наблюдатель, администратор)
- агрегированные отчёты и мониторинг

Архитектура учитывает эти сценарии, но они не реализуются в MVP.

## 5. Ядро (Core Engine)

### 5.1. Назначение

Ядро — это единственный компонент системы, который:
- хранит данные
- проверяет корректность операций
- изменяет состояние склада

### 5.2. Область ответственности

Ядро управляет:
- позициями
- количествами
- локациями
- движениями (приёмка, перемещение, списание)

### 5.3. Ограничения

Ядро **не знает и не должно знать**:
- естественных языков
- LLM
- интерфейсов
- форматов пользовательского ввода
- изображений и аудио

### 5.4. Интерфейс ядра

Ядро принимает только структурированные команды:

```json
{
  "command": "intake",
  "payload": {
    "items": [
      { "item_id": "pm_pistol", "qty": 1, "location": "сейф в кабинете" },
      { "item_id": "9mm_ammo", "qty": 28, "location": null }
    ]
  }
}
```

Инварианты ядра (MVP):
- intake: `items` — непустой список, `qty > 0`, `location` допускает `null`; при первом появлении `item_id` создаётся в справочнике.
- move: `qty > 0`; предмет и остаток на `from` должны существовать, иначе ядро возвращает ошибку (LLM/интерфейс транслируют пользователю причину).

## 6. LLM слой
### 6.1. Назначение

LLM используется как интерпретатор пользовательского ввода.

Он:
понимает текст
работает с транскрибированным голосом
анализирует изображения
нормализует сущности
формирует предложения или команды
LLM не выполняет операции над складом напрямую.

### 6.2. Роли LLM

LLM может находиться в одном из состояний:
Interpretation — анализ ввода
Proposal — предложение действий
Confirmation — ожидание подтверждения
Command generation — формирование команды для ядра
Fallback — безопасный отказ при ошибке

---

## 7. Обработка изображений (Image Flow)
### 7.1. Основное правило

Изображение никогда не приводит к немедленному изменению склада.
Любая обработка изображения проходит через этап предложения и подтверждения.

### 7.2. Поток обработки изображения

Пользователь отправляет изображение (с подписью или без)
Media слой сохраняет изображение и формирует URL
Файлы хранятся в каталоге media конкретного склада (изоляция по складам)
LLM получает:
URL изображения
сопутствующий текст (если есть)
LLM формирует черновой список предметов
Пример результата LLM:

```json
{
  "type": "proposal",
  "items": [
    { "item_id": "pm_pistol", "qty": 1 },
    { "item_id": "9mm_ammo", "qty": 28 },
    { "item_id": "nut", "qty": 4 },
    { "item_id": "bolt", "qty": 8 }
  ]
}
```
Пользователю задаётся вопрос на подтверждение:
«Додати все на склад?»
Только после явного подтверждения формируется команда ядру.

### 7.3. Приёмка с изображения

предметы добавляются без локации
дальнейшее размещение выполняется отдельными командами
подтверждение пользователя обязательно
в movements.meta сохраняются: URL изображения, подпись (если была), черновой список, вероятность/уверенность (при наличии)

---

## 8. Обработка голоса

Аудио принимается как файл или URL
Media слой транскрибирует аудио в текст
Текст передаётся LLM вместе с ссылкой на аудио
Далее процесс идентичен текстовому вводу
Текст всегда сохраняется и используется как основной источник.
Транскрипт и ссылка на файл записываются в movements.meta.

---

## 9. Knowledge слой

Отдельный слой доменных знаний, используемый LLM:
идентификаторы предметов
синонимы
маппинг локаций

Этот слой:
может расширяться
может обновляться пользователем (в будущем)
не используется напрямую ядром
Ядро работает только с нормализованными идентификаторами.
В MVP наполнение ведётся вручную (общий словарь), в будущем появятся локальные словари складов с более высоким приоритетом над общим.

## 10. Интерфейсы

Интерфейсы являются тонкими адаптерами и не содержат бизнес-логики.

Поддерживаемые и планируемые интерфейсы:
CLI (основной)
Telegram
WhatsApp
Android-приложение

Интерфейсы:
принимают ввод
передают его в общий пайплайн
отображают ответы пользователю

---

### 11. CLI

CLI — основной инструмент разработки, тестирования и отладки.

CLI поддерживает:
текстовый ввод
ввод JSON напрямую в ядро
пути к файлам
URL изображений и аудио

CLI моделирует поведение реального пользователя и мессенджеров.

### CLI - root
В CLI есть служебные команды для администратора. они начинаются с "+"

например:
+deletestorage sklad_old
+liststorages
+status

Если такая команда (с плюсом) будет получена из другого интерфейса (мессенжера) - она не обрабатывается.

### CLI promt

CLI prompt должен динамически отражать активный склад. 

```
bot:sklad_fuel> 
```

## 12. Error Handling (MVP)
### 12.1. Основной принцип

Если система не уверена — она ничего не делает.

### 12.2. Поведение при ошибках

Ошибка может возникнуть если:
ввод не интерпретируется
данные неполные
команда невалидна
LLM не уверен в намерении

В этом случае:
команда в ядро не отправляется
состояние склада не изменяется
пользователю возвращается нейтральный ответ

Пример:
«Я не зовсім зрозумів запит. Будь ласка, спробуйте переформулювати.»

### 12.3. Ограничения MVP

нет детальной классификации ошибок
нет обучения на ошибках
нет сложных уточняющих диалогов
Эти механизмы будут добавлены на следующих этапах.

## 13. Тестирование
### 13.1. Основное правило

Каждый тест работает с новым, пустым складом.

### 13.2. Типы тестов

Core tests:
прямые команды ядра
без LLM
быстрые и детерминированные

Scenario tests:
пользовательские сценарии
текст, голос, изображения
LLM может быть включён или отключён

Manual tests:
ручное тестирование через CLI
наблюдение за состоянием склада

## 14. Configuration Management

The system follows a strict no-magic-numbers policy.

All parameters that may affect behavior, limits, thresholds,
or environment-specific behavior must be configurable.

### Configuration Levels

1. Global configuration
   - base defaults for the whole system

2. Storage-level configuration
   - optional overrides per storage
   - only explicitly defined values override global defaults

Configuration is resolved using a cascading merge strategy.

### Principles

- business logic never hardcodes configurable values
- configuration is read-only for core logic
- missing values always fall back to global defaults
- configuration files are explicit and human-readable

This approach allows:
- per-storage customization
- safe experimentation
- predictable behavior across environments
