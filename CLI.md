# Назначение CLI

CLI предназначен для:
- отладки
- тестирования
- административных операций
- ответственных массовых действий

CLI не является пользовательским интерфейсом.

## Разделение вывода

Система различает два типа вывода:

### System Output
Используется для отладки и администрирования:
- логи
- ошибки
- промежуточные структуры
- команды, передаваемые в ядро

### User Output
Человеко-понятный текст, предназначенный для пользовательского интерфейса.

CLI-интерфейс отображает оба типа вывода раздельно:

```
-------- SYSTEM:
Технічна інформація:
- логи
- помилки
- відповіді ядра
- службові дані
- трасування
-------- USER:
Людська відповідь, яку побачить кінцевий користувач
(через додаток, месенджер тощо).
```


Користувач **ніколи не бачить** секцію SYSTEM.

---

## Роль CLI у LLM-архітектурі

CLI використовується як:
- інструмент розробника
- вікно спостереження за роботою LLM
- спосіб дебагу користувацьких сценаріїв

Через CLI можна вводити запити так, як це робив би користувач,
і бачити повну картину: від інтерпретації до виконання.

# CLI Commands (skeleton)

- `exit` — завершает работу CLI.
- `quit` — завершает работу CLI.

## JSON команды

- Если нет активного склада, JSON-команды запрещены (сообщение: `No active storage. Use +activatestorage first.`).
- Если ввод начинается с `{`, CLI переключается в режим сбора JSON: используется альтернативный промпт (`... ` по умолчанию), копятся строки.
- Сбор завершается, когда баланс фигурных скобок выравнивается или введена пустая строка.
- После этого CLI пытается распарсить собранный текст через `json.loads()`; если это dict — добавляется поле `storage_id` с активным складом и команда передаётся в `core.engine.handle_command`.
- Ответ ядра (dict) печатается в виде JSON.
- При ошибке парсинга выводится нейтральное сообщение, CLI остаётся в рабочем состоянии.
- Обычный текст, не начинающийся с `{`, передаётся в LLM-оператор:
  - SYSTEM: полный трассинг (snapshot, сырой JSON LLM, команды, ответы ядра)
  - USER: дружелюбный ответ на украинском

## Admin-команды (префикс `+`)

- `+createstorage <storage_id>` — создаёт новый склад (если уже существует — сообщение).
- `+deletestorage <storage_id>` — удаляет склад; если удаляется активный, активный сбрасывается.
- `+liststorages` — выводит список складов и помечает активный. Алиас: `+ls`.
- `+listitems` — выводит содержимое активного склада в табличном виде (item, location, qty, unit). Локация `null` отображается как `(unplaced)`. Кількість показується без десяткової частини для цілих значень і округляється для дробових. Длинные значения усекаются и дополняются `...` по `cli.table_max_width` (по умолчанию 24). Алиас: `+li`.
- `+activatestorage <storage_id>` — делает склад активным (ошибка, если склада нет). Алиас: `+as`.
- `+status` — выводит состояние CLI (активный склад, backend, количество известных складов).
- `+runscenario [--isolated] <file>` — выполняет шаги сценария из JSON-файла; `--isolated` создаёт временный склад, активирует его на время сценария и удаляет после завершения.
- `+outsystemshow` — включает SYSTEM-вывод для LLM-ответов CLI. Алиас: `+oss`.
- `+outsystemhide` — отключает SYSTEM-вывод для LLM-ответов CLI. Алиас: `+osh`.

Backend выбирается конфигом (`storage.backend`): `memory` (по умолчанию) или `sqlite`
с именем файла `storage.sqlite_filename` (по умолчанию `storage.db`), который создаётся
в каталоге склада. Статус показывает текущий выбранный backend.

## Prompt

Промпт формируется по шаблону `cli.prompt_template` (по умолчанию `bot{storage}> `):
- без активного склада: `bot>`
- с активным складом, например `sklad_fuel`: `bot:sklad_fuel>`

SYSTEM-вывод для LLM по умолчанию настраивается через `cli.show_system_llm` (по умолчанию `false`).

## Default storage

Если в `.env` задан `DEFAULT_STORAGE`, CLI при старте активирует этот склад, если он существует.
Если склад не найден, CLI пишет предупреждение и остаётся без активного склада.
